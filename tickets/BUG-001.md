## Observed behaviour
Found in review of TASK-002, in `src/backend/MiniWms.Api/Program.cs` and its tests:
1. **CORS lost on errors (suspected; NOT reproduced).** `UseExceptionHandler` and `UseStatusCodePages` run before `UseCors`. The review expected the 500 and 404 `application/problem+json` responses for a request from `http://localhost:4200` to carry no `Access-Control-Allow-Origin` header. The before-the-fix run showed they do carry it on .NET 10, so this is not a defect of this host. The `UseCors` reordering is kept as hardening, and AC 1 to 4 are guard tests that pass before and after the fix.
2. **Generic problem types.** `CustomizeProblemDetails` gives every status other than 404 and 500 the type `error` and the framework's default title, so a 400, 401, 403 or 409 looks the same as a 500. ADR-003 lists the types `validation`, `conflict`, `not-found`, `unauthorized`, `forbidden` and `error`.
3. **No correlation id.** The customizer clears all extensions, including `traceId`, so a client cannot match an error with a server log line.
4. **Weak tests.** The CORS tests send only a simple GET (no preflight, no Origin on an error response), so finding 1 passes the suite. The "no stack trace" tests match the substrings " at " and "Exception" in the body, which is brittle both ways.

## Expected behaviour
- Every error response, including 404 and 500, carries the CORS headers for `http://localhost:4200` and none for any other origin.
- Problem types follow ADR-003 by status; unknown statuses stay `error`.
- Every error body carries a `traceId` for correlation and still has no `detail`, exception text or stack trace; the 500 title stays generic.
- Tests prove all of this and fail on the old behaviour.

## Steps to reproduce
1. Start the API host in a test (or `dotnet run --project src/backend/MiniWms.Api`).
2. Send `GET /api/v1/does-not-exist` with the header `Origin: http://localhost:4200`.
3. Observe: `404 application/problem+json` with `Access-Control-Allow-Origin: http://localhost:4200` (the suspected missing header does not reproduce). The same holds for a route that throws (500).
4. Send a request that returns 409 (or 400, 401, 403): the body has `type: "error"`.

## Acceptance criteria
1. Given a request with `Origin: http://localhost:4200` to an unknown route, when the API answers 404, then the response has `Access-Control-Allow-Origin: http://localhost:4200` and an `application/problem+json` body.
2. Given a request with `Origin: http://localhost:4200` to a route that throws, when the API answers 500, then the response has `Access-Control-Allow-Origin: http://localhost:4200`, an `application/problem+json` body and the generic title "An unexpected error occurred.".
3. Given an error response (404 or 500) for a request from any other origin, when it is returned, then it carries no `Access-Control-Allow-Origin` header.
4. Given a preflight `OPTIONS /api/v1/health` from `http://localhost:4200` with `Access-Control-Request-Method: GET` and a request header, when it is answered, then it succeeds with `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers`; from another origin it carries no `Access-Control-Allow-Origin`.
5. Given error responses with status 400, 401, 403, 404, 409 and 500, when they are written, then `type` is `validation`, `unauthorized`, `forbidden`, `not-found`, `conflict` and `error` respectively, and any other status has type `error`; `status` always equals the HTTP status.
6. Given any `application/problem+json` error response, when it is returned, then the body has a non-empty `traceId` string, no `detail` and no `instance`, and for 500 the title stays generic.
7. Given the "no stack trace" tests, when they check an error body, then they assert its structure (only the properties `type`, `title`, `status`, `traceId` and, for validation, `errors`) and that the exception's secret text is absent, not substring matches on " at " or "Exception".
8. Given the regression tests, when they run against the code before the fix, then the tests for AC 5 and AC 6 fail (the real defects: problem types and `traceId`), while the CORS tests for AC 1 to 4 pass as guards because the suspected CORS defect does not reproduce on .NET 10; after the fix all pass (record the before-and-after result in the report). *(Amended by the owner on 2026-11-19: the original text required AC 1, 2 and 5 to fail before the fix; the before-run showed AC 1 and 2 pass.)*
9. Given the whole change, when `dotnet build src/backend` and `dotnet test src/backend` run, then the build has 0 warnings and every test passes, each AC-proving test tagged `[Trait("AC", "BUG-001.<n>")]`.

## Out of scope
- Moving the duplicated `RepoLocator` test helper into a shared project (it needs a new project, which is an ADR-001 decision).
- Hook and harness hardening (review findings 4 to 6); those are a separate `setup/` change.
- Validation error bodies (the `errors` object) beyond keeping the type `validation`; they arrive with the module tickets.
- Auth, database access and module endpoints.

## Notes and links
- Fix idea from the review: register `UseCors` before `UseExceptionHandler` and `UseStatusCodePages` (the CORS policy is already named in `Program.cs`).
- Keep `traceId` from `context.HttpContext.TraceIdentifier` (or the current activity id) when clearing other extensions.
- Test-only routes returning 400, 401, 403 and 409 can be added to the test factory (`ThrowingApiFactory` style) without touching production code.
- Record AC results in `docs/reports/BUG-001/ac-results.md` and one row in `docs/reports/ac-log.md`.
